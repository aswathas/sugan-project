How a share moves

Three moments from send to receipt

Encrypted in your browser

Before upload begins, your browser hashes the file, encrypts it with a fresh 256-bit AES-GCM key, and wraps that key to the recipient’s RSA-OAEP public key.

The server holds only ciphertext

Only the encrypted bytes, wrapped key, IV, and share metadata reach the server, shown beside the original header bytes in the cipher strip.

Proved afterwards

After decryption, the recipient’s browser recomputes the SHA-256 fingerprint and verifies the sender’s ECDSA signature, marking the card verified.

Questions before you sign up

Does the server ever see my file?

No. Your browser hashes the plaintext with SHA-256, encrypts the bytes with a new 256-bit AES-GCM key, and wraps that key to the recipient’s RSA-OAEP public key before uploading. The server stores only ciphertext and metadata.

What happens if I lose my device?

During registration your browser generates a 12-word recovery phrase, encrypts your private key with a key derived from that phrase via PBKDF2-SHA-256, and uploads the encrypted backup. On a new device, click “Restore my key on a new device” when signing in; the phrase itself never goes to the server and cannot be reset.

Can the sender read the file after sending it?

Not from the server. The file key is wrapped only to the recipient’s public key (and optionally to a share password of at least 10 characters), so the sender’s private key cannot decrypt the server copy. The sender can still revoke an unopened share or delete it.

What does it cost?

Nothing. SecureShare is free to use, with no card required, and runs encryption directly in your browser using the Web Crypto API.

How does the recipient know the file was not altered?

After decrypting the ciphertext, the recipient’s browser recomputes the SHA-256 digest and verifies the sender’s ECDSA P-256 signature over the parties, filename, size, digest, IV, permission, and expiry.
