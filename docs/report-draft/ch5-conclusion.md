# Chapter 5 Conclusion

## 5.1 Review of the Work

This report has described the design, implementation and verification of SecureShare, a web-based file-sharing system that keeps the storage server outside the cryptographic path of the files it holds.

Chapter 1 set out the problem: conventional file sharing treats the storage server as a trusted party, so a compromise, an insider or a compelled disclosure exposes the documents themselves rather than an unreadable container. It stated five objectives and fixed the scope of the work, including the honest boundary around the access-control claim.

Chapter 2 placed the work in the literature. The surveyed systems achieve fine-grained access control over encrypted files through attribute-based encryption, sometimes combined with blockchain, provenance or lattice-based constructions. Each is more expressive than the present prototype, and each depends on infrastructure that a zero-cost localhost build cannot provide. The chapter then contrasted the conventional and end-to-end encrypted models, presented the literature survey table, and derived the mathematical relations on which the implementation rests: key generation, the AES-256 key space, the ciphertext relation, the key-wrapping relation, the recovery relation, the authentication-tag forgery bound and the entropy argument for the one-time code.

Chapter 3 described the design: seven modules, including the server-side Google verifier, a three-column logical architecture with two trust boundaries, the hardware and software requirements, the stage-wise development, the seven-step working principle with the lifecycle that follows a send and the four flows for signing, password wrapping, recovery and the second factor, the data held by the server, the complete HTTP interface including the three key endpoints, the hardening controls and the two-layer testing procedure. It also described the file-drive workspace as the interface of the system, since the five-section rail, the search box, the sorting, the two view modes, the selection and bulk actions, the per-user starring, the trash, the keyboard shortcuts, the drag to share, the theme and the storage breakdown are now part of how a user sees the state of a share, and it described the lifecycle by which a share moves from live to revoked, expired or trashed. The sign-in page carries the anatomy of the product, and its central piece is a drawing: an isometric machine, built with the anatomy kit, in which a file arrives on a carriage, a key is turned on a dial, a head comes down and presses the file into a sealed capsule, and the capsule slides into the hopper that stands for the server. The hopper only ever holds capsules, because the file was consumed by the seal, so the figure states the claim of the project as a machine that works rather than as a sentence that promises.

Chapter 4 reported the results. `npm test` completed with twenty-one checks passing and the headless browser test with twenty-seven. The tests established that an unverified account cannot sign in, that a wrong code and a wrong password are rejected, that the access code gates registration, that the stored blob contains no plaintext, that the private key in the browser is non-extractable, that the recipient decrypts to the original bytes and that an unrelated user is refused with 403. They further established that an expired share and a revoked share refuse their bytes with 410, that only the sender can revoke, that an opened share cannot be revoked, that the activity trail records the events and hides another account's, and that the chain verification endpoint reports the chain intact. They also established the abuse controls, that repeated failed sign-ins and wrong one-time codes are locked out, and that signing out everywhere ends the account's sessions. The Google suite showed that a valid token signs a user in and that a token with a wrong audience, issuer, expiry, signature or structure is refused. They further established the share lifecycle and the workspace: starring is per user, a deleted share leaves the ordinary views and enters the trash where its bytes are refused, a restore brings it back, and a purge removes it for good; the rail shows the starred and trashed sections with their counts, selecting a card shows the bulk bar, and the theme and the storage breakdown behave as described. The browser layer further established that each account has a twelve-word recovery phrase and a wrapped private key on the server, that the sender's signature verifies when the recipient opens the file, and that a password-protected share refuses the wrong password and opens with the right one. They also established that an account with a second factor cannot be opened by the password alone, that the factor can be turned on from the interface and read by any authenticator app, and that the anatomy of the product is one component mounted on the sign in page and inside the workspace. The chapter then discussed what the new features buy and what they cost, and listed the limits of the prototype.

## 5.2 Conclusions

The work supports the following conclusions.

A file-sharing system can be built in which the server is structurally incapable of reading the files it stores. The mechanism is not a promise by the application but a consequence of where the keys live: the private key is generated in the browser, is non-extractable, and never reaches the server; the AES key for each file exists only in wrapped form on the server. The tests confirmed the observable consequence, that the blob on disk contains no plaintext and that only the recipient can decrypt it.

Hybrid encryption is the right construction for this problem. Encrypting the file with AES-GCM 256 and wrapping only the short symmetric key with RSA-OAEP gives the speed of a symmetric cipher for the bulk data and the key-distribution convenience of public-key cryptography for the key. It also gives per-recipient encryption naturally: because the symmetric key is wrapped to the recipient's public key, the same file shared to two recipients produces two different wrapped keys and two independent ciphertexts.

Key custody on the client is both the strength and the cost of the design. It is the strength because it removes the server from the trust boundary entirely. It is the cost because a lost device would otherwise be a lost private key and therefore a lost archive. The recovery phrase is the answer to that cost, and it is stated next.

A recovery phrase can make a device replaceable without giving the server the ability to read the files. At registration the private key is exported, encrypted under a key derived from twelve words, and stored on the server as a blob the server cannot open, so a new device can fetch it after the user signs in and enters the phrase. The phrase has limits of its own. Twelve words drawn from a list of 128 give 84 bits of entropy, enough to resist an online guess and less than a modern password manager, and a phrase written down is a secret on paper. Because the server holds the encrypted blob, a server compromise exposes it to an offline attack on the phrase, which is why the derivation is deliberately slow. The phrase is shown once and the server cannot reset it, so a user who loses both the phrase and the device has still lost the archive.

Authentication with a password and a time-limited one-time code is sufficient for the prototype and honest about its mechanism. The password is hashed with scrypt, the code is hashed and discarded, and the session is a server-side token in an HttpOnly cookie. The code is a second factor against a disclosed password, not a substitute for one, and its entropy is adequate only because its validity window is short and its attempts are controlled.

Sender-controlled access control is useful and is implemented, but its guarantee is narrower than its name suggests. The view permission prevents the ordinary interface from offering a saved copy; it cannot prevent a determined recipient from retaining the plaintext, because with end-to-end encryption the recipient necessarily holds the plaintext at the moment of display. The one exception is a share the sender protects with a password. The file key is then wrapped twice, once under the recipient's public key and once under a key derived from the password, so the file cannot be decrypted at all without the password. The interface rule still applies to the download button, and the password closes the gap at the point of decryption, but a recipient who holds the password and the plaintext can still keep a copy. This is a property of the architecture and not a defect of the implementation, and it should be stated wherever the feature is described. The self-destruct timer and revocation are a different case: they are enforced where the bytes are served, so a share whose time has passed or whose sender has called it off cannot be fetched at all, and neither claims to have deleted a copy that was already collected.

The integrity check is worth having in its own right. Comparing a SHA-256 fingerprint of the plaintext, computed by the sender and recomputed by the recipient, establishes that the file recovered is the file that was sent, which AES-GCM alone does not say. Its cost is that the fingerprint has to be stored and returned by the server, so the server holds a content hash of each plaintext and is itself the party that supplies the value for comparison. The feature answers a question about the bytes; it does not answer who authored them. That second question is now answered by the share signature, and the two checks are complementary rather than interchangeable.

A signature over the share metadata can establish who vouched for a file without the server being able to produce that signature. Each account has an ECDSA P-256 signing key pair beside its RSA key pair, and the sender's browser signs the string `from|to|filename|size|sha256 of the plaintext|iv` when the share is made; the recipient's browser rebuilds the same string from the metadata and verifies the signature against the sender's published signing key. The chain is the point: the signature covers the plaintext fingerprint, and the fingerprint covers the bytes that arrived after decryption, so the signature proves who vouched for the file while the fingerprint proves that the file is the one that was vouched for. One check alone would not answer both questions. The signature is over metadata and not over the ciphertext, so an attacker who holds the server's data cannot forge a different file under the same signature, but the server can still refuse to deliver a share it has been told to refuse. The signing key is a software key held in the same browser store as the encryption key, so it is not hardware backed, and a compromise of the device compromises both.

A hash-chained audit trail makes the record of what happened tamper-evident without making it independent. Each entry carries the SHA-256 of the entry before it, so an edit or a deletion leaves a break that the verification endpoint finds, and the trail is filtered per account so that one user's events are never shown to another. But the chain is written and checked by the same process that it describes, so an operator who rewrites the whole chain produces a chain that verifies. It is evidence of what the server recorded, not independent proof of what the server did.

The share lifecycle is enforced at the point where the bytes are served, and that is what makes it more than a label. A share is live, revoked, expired or trashed, and the server derives the state from the record. In every resting state it refuses the bytes while the metadata stays visible, so the interface can say what happened and why. The trash makes deletion reversible: a share that is moved to it can be restored to the ordinary views while it is still valid, and the sender alone can purge it, which removes the record and the ciphertext file. The result is a lifecycle that a user can operate without the server ever reading a file, and one whose irreversible step is explicit rather than implied.

The file-drive workspace is the part of the system that makes the lifecycle legible. A rail of counted sections, a search, a sort, a grid and a list view, a selection bar with bulk actions, per-user starring, a reversible trash, keyboard shortcuts, drag to share, a remembered theme and a storage breakdown are all interface work rather than cryptography, but they decide whether a user can find a share and understand its state. Starring is per user because the server records who starred a share, so the sender and the recipient can use the same shortlist control without affecting one another. Presence is deliberately only a last-seen note: the server records when an account was last active and returns it with the public key, so the people list can say when someone was last seen without a websocket or a persistent connection, and it does not claim to know who is online now.

Authentication can be widened without widening the trust placed in the client. The Google route accepts an identity asserted by a third party, and the token is verified on the server, not in the page, because a page that vouches for itself vouches for the party whose identity is in question. The negative cases carry the weight: a token with a wrong audience, a wrong issuer, an expired time, a tampered payload, a forged signature or a malformed structure is refused before a session exists. The cost is an optional external dependency, and the one-time code remains the path that works with nothing configured.

The system meets the client's cost constraint without compromise to the security claim. It installs no packages, uses no paid service and runs on a machine with Node.js and a browser. The one-time code is delivered by a mailer that prints it locally by default and can be switched to a free email provider with one environment variable. The Google verifier was written against `node:crypto` and the built-in `fetch` rather than an identity library, so it too adds no package. This is why the demonstration is repeatable without an account anywhere.

## 5.3 Recommendations for Future Work

The following recommendations would take the prototype towards a system that could be operated as a service. The audit trail, revocation, expiry, the plaintext integrity check, the sender's signature, the password on a share, the recovery phrase, the file-drive workspace, starring and the trash are no longer on this list: they are part of the system as built and were verified in Chapter 4. What remains is what the prototype genuinely does not do.

**A signing key that is hardware backed.** The signing key is a software key in the same browser store as the encryption key, so a compromise of the device compromises both, and a recipient's verification establishes what that browser vouched for rather than what a device did. A key held in a hardware security key or a platform secure enclave, with the signature made inside the hardware, would make the private half far harder to copy and would let the published signing key stand for a device the sender physically holds. It would also give the account a way to demonstrate that the key it publishes belongs to hardware the sender controls.

**A recovery scheme that does not depend on a written phrase.** The recovery phrase makes a device replaceable, but it is a secret the user has to transcribe and keep, and a phrase written down is only as safe as the paper it is on. A scheme in which the wrapped key is split among several trusted parties, or held by a second device that the user controls, would recover an account without a single low-entropy secret that has to be stored by hand. It would also remove the offline attack on the phrase, because there would be no phrase to attack.

**Forward secrecy through short-lived session keys.** The present design wraps a long-lived public key. A ratcheting or ephemeral-key protocol would ensure that the compromise of a long-term key does not expose past shares, at the cost of additional key management in the client.

**A deployment that survives the loss of the node.** The prototype runs on localhost over plain HTTP, with a single JSON store and a single blob directory on one machine. A deployment with a proper certificate would protect the session cookie and the ciphertext in transit, and replication and backup across more than one node would let the service survive the loss of the machine it runs on. The development tunnel used for a remote demonstration rotates its public address on each start and terminates no TLS itself, so it provides neither a stable address nor a certificate. Without these, the confidentiality of the ciphertext is preserved, but the session, the transport and the availability of the service are not protected, and the system should not be operated in that state.

**Fine-grained attribute-based policies.** The current access model is a single per-file permission of view or download, and that permission is an interface rule rather than a cryptographic one except where the sender adds a password to the share. The literature reviewed in Chapter 2 shows that attribute-based encryption can express much richer policies over encrypted data. Replacing the single permission with a policy, so that a file is readable only by users holding a specified set of attributes, is the natural extension of the work and the point at which the surveyed literature becomes directly applicable. It is also the step that would make the permission enforceable rather than advisory.

**A live presence channel.** Presence is currently a last-seen note: the server records when an account was last active and the people list reports it, which is honest but not live. A websocket or a long-poll channel would let the list show who is reachable now, at the cost of a persistent connection and the dependency that the present design deliberately avoids. It is a genuine feature the prototype does not have, and it should be added only where the connection cost is acceptable.

Taken together, these recommendations describe a path from a verified localhost prototype to a service. The prototype's contribution is to show that the central property, a server that cannot read the files it holds, is achievable with primitives that are already present in every browser and in Node.js, at no cost and without a dependency. The features added since the first draft, revocation, expiry, the integrity check, the sender's signature, the password on a share, the recovery phrase, the tamper-evident trail, the file-drive workspace, per-user starring and the reversible trash, show that the property survives contact with the operational requirements a real sharing tool imposes.
