# Chapter 3 System Design and Methodology

## 3.1 Proposed System

SecureShare is a web application with two cooperating halves: a Node.js server that stores accounts, share metadata and ciphertext, and a browser client that performs all cryptography. The design is deliberately small. It contains no framework, no database engine and no third-party package; the server is written against the `node:http` and `node:crypto` modules, and the client is plain JavaScript using the Web Cryptography API and IndexedDB. This choice was made so that the system can be run on any machine that has Node.js, without an installation step, and so that nothing in the system depends on a paid service.

The system is organised into seven functional modules.

The **registration and authentication module** accepts a username, an email address and a password, hashes the password with scrypt and a per-user salt, and issues a six-digit one-time code. The account is created in an unverified state and cannot be used until the code is verified. Verification creates a server-side session token and sets it in an HttpOnly cookie. When an access code is configured, registration requires it before any other field is examined. Where Google sign-in is configured, the module also links a verified Google subject to an account and starts a session by the same token mechanism.

The **identity verification module** is `server/google.js`. It verifies a Google ID token on the server. It checks that the token uses RS256, that its issuer is Google, that its audience is this application's client id and that it has not expired, and it verifies the signature against Google's published signing keys, which are cached for an hour. The verification is placed on the server because a token checked only in the page proves nothing about the party who controls that page. Node's built-in `node:crypto` performs the signature check and the built-in `fetch` retrieves the keys, so the module adds no package.

The **key management module** runs in the browser. At registration the browser generates an RSA-OAEP 2048-bit key pair, extractable once so that a recovery copy can be exported, and, beside it, an ECDSA P-256 signing key pair. The device keeps non-extractable copies of both private keys in IndexedDB and sends only the two public keys to the server, each encoded in SPKI form. The RSA public key is published as the account's encryption key and the ECDSA public key as its signing key. The module also generates a twelve-word recovery phrase, derives a key from it with PBKDF2, and uses that key to encrypt an exportable copy of the RSA private key. The encrypted copy is uploaded to the server and kept in the browser, while the device keeps the non-extractable copy for daily use.

The **sharing module** also runs in the browser. For each share it generates a fresh AES-GCM 256-bit key and a random 96-bit initialisation vector, encrypts the selected file, and wraps the AES key with the recipient's public key. It computes a SHA-256 fingerprint of the plaintext, so that the recipient can check the file it recovers, and signs the string `from|to|filename|size|sha256 of the plaintext|iv|permission|expiry` with the sender's ECDSA private key. The permission and the expiry are inside the signature because the recipient relies on both: the permission decides whether the file may be saved, so a server that quietly changed it would break the signature instead of quietly granting it. Where the sender chooses password protection, it also derives a key from the password with PBKDF2, SHA-256 and 210,000 iterations over a random sixteen-byte salt, and wraps the AES key a second time under that key with AES-KW. It uploads the ciphertext, the initialisation vector, the wrapped key and the second wrapped key when there is one, the fingerprint, the signature, the protection mode, the salt when there is one, the expiry moment, and the descriptive metadata.

The **access-control module** records, for each share, the permission that the sender chose: view or download. The permission is stored with the share, returned to the sender and the recipient, and reflected in the interface when the share is opened. The module also records the expiry moment the sender chose and any revocation the sender later applies. A share is therefore live, expired, revoked or trashed, and the server refuses its bytes in every state but live while still returning its metadata so that the card can say why. Deleting a share moves it to the trash; from there it can be restored to the ordinary views, or purged, which removes both the record and the ciphertext file.

The **storage module** is the server's JSON store and blob directory. It holds user records, session records, share records, the audit trail and one ciphertext file per share. A user record carries the two public keys and the wrapped private key backup with its salt and initialisation vector; a share record carries the signature, the protection mode with its salt and its second wrapped key when there is one, the expiry moment the sender set, and the number of ciphertext bytes the server actually stored.

The **presentation module** is the browser interface, and it is arranged as a workspace in the shape of a file drive. A left rail carries five sections with their counts: Shared with me, Sent by me, Starred, Recent and Trashed. The same rail shows how much ciphertext the account holds on the server and how that total splits by file type. A search box in the band filters the current view by file name, and a sort control orders the view by name, newest, oldest or size. The cards can be shown as a grid or as a list, and the choice is remembered between visits.

Each card carries the filename, the other party, the size, the time, the permission badge, the self-destruct state, a live mark while a share has not been opened and a checkbox for selection. Selecting one or more cards reveals a bar with the count and the actions Star, Revoke, Delete and Clear, so that the same operation can be applied to a group. Starring is per user: the server records who starred a share, so the sender and the recipient can star the same share differently. Deleting a share moves it to the trash, where it can be restored or purged for good. A New route opens the send panel, and a card can be dragged onto a recipient in the people list to open that route with the file and the person already filled in. Keyboard shortcuts follow the file-drive convention: slash focuses the search box, n opens the New route, j and k move the highlighted card, Enter opens it and Escape clears the selection. A button in the band switches between the paper theme and a dark theme, and the choice is remembered; the dark theme is one override of the colour tokens rather than a second stylesheet. The same page carries the evidence panel and the activity trail.

Three additions sit on the same page. The send route offers an **Extra protection** choice of Key only or Password too, and reveals a password field when the second is chosen. A password panel appears when a protected file is opened, and the file cannot be decrypted without it. After registration a recovery phrase panel shows the twelve words with a copy button, and the sign in screen carries a restore my key on a new device line that reveals a phrase field.

Nothing in this list holds a private key in usable form, an AES key or plaintext on the server. That is the defining property of the design and the reason the modules are separated as they are. The server does hold two values that deserve care. One is the SHA-256 fingerprint of each plaintext. The other is one encrypted copy of each account's RSA private key, wrapped under a key derived from the recovery phrase, with its salt and initialisation vector. Neither can be used without material the server does not hold, and both are treated as limits in Chapter 4 rather than as secrets.

## 3.2 Logical Architecture

Figure 3.1 shows the logical architecture. The diagram has three columns: the sender's browser on the left, the server in the centre, and the recipient's browser on the right.

Figure 3.1 Logical architecture of the proposed secure file-sharing system

[FIGURE: docs/figures/01-architecture.svg]

The sender's browser holds the file that is to be shared, the user's encryption and signing key pairs, and the encryption, wrapping and signing functions. Each key pair has two parts with different fates: the private key remains in IndexedDB on the device, and the public key has been published to the server. When a share is made, the sender's browser runs AES-GCM encryption under a newly generated key, then runs RSA-OAEP wrapping of that key under the recipient's public key. Where a password is chosen, it wraps the same key a second time under a key derived from the password. It also signs the share metadata with the signing key. The values that leave this column are the ciphertext, the initialisation vector, the wrapped key or keys, the signature, the protection mode and its salt.

The server column holds three things: accounts with their public keys and wrapped private key backups, share metadata, and ciphertext blobs. It holds no private key in usable form, no AES key and no plaintext. The server's role is to authenticate sessions, to keep the directory of public keys so that a sender can address a recipient, to record who shared what with whom under which permission, and to return a ciphertext blob to a user who is entitled to it. It relays the signature but cannot produce or check it, because it never holds the signing private key. The marker on the server in Figure 3.1 states this limitation explicitly.

The recipient's browser column holds the recipient's private key in IndexedDB, the unwrap, decrypt and verify functions, and the download or view step. The recipient's browser receives the ciphertext, the initialisation vector, the wrapped key and the signature, recovers the AES key with the private key, decrypts the ciphertext, and presents the file. Where the share is password protected, it also derives the same key from the password and recovers the AES key from the second wrapped copy, then checks that the two recovered keys are identical before it decrypts. Neither wrap alone opens the file. It rebuilds the signed string from the metadata and verifies the signature against the sender's published signing key before it reports the file as verified.

Two trust boundaries are visible in this arrangement. The first separates each user's browser from the server: the usable private key and the plaintext never cross it. The second separates the two browsers from each other: the recipient obtains the file only by decrypting with the private key that belongs to the addressed account. The server is inside neither boundary with respect to file content; it is a relay.

## 3.3 Hardware Requirements

The prototype was developed and demonstrated on ordinary hardware. Table 3.1 lists the requirements.

Table 3.1 Hardware requirements

| Component | Requirement |
|---|---|
| Processor | Any 64-bit processor capable of running a current browser and Node.js |
| Memory | Sufficient for the operating system and one browser with two profiles; no special requirement |
| Storage | A small amount of disk space for the JSON store and the ciphertext blobs, proportional to the files shared; the interface accepts files up to 25 MB |
| Display | A standard display for the browser interface |
| Network | Not required for a localhost demonstration; a local network or a development tunnel is sufficient for a two-machine demonstration |

Because the cryptography runs in the browser and the server performs no cryptographic work beyond password hashing and token generation, the system does not demand a powerful machine. The heaviest operations are the RSA key generation at registration and the AES encryption of the selected file, both of which are performed on the client.

## 3.6 Working Principle

The working principle of SecureShare is a sequence of seven steps, followed by the lifecycle that a share can enter after it has been sent. Figure 3.2 shows the sequence and indicates which steps run in the sender's browser, on the server and in the recipient's browser.

Figure 3.2 The seven-step working principle of SecureShare

[FIGURE: docs/figures/05-working-principle.svg]

**Step 1: User authentication.** A user registers with a username, an email address and a password. The browser generates the user's RSA-OAEP encryption key pair and ECDSA P-256 signing key pair during registration, keeps both private keys locally in non-extractable form, and publishes both public keys. Registration also produces a twelve-word recovery phrase and a wrapped copy of the private key, described below. The server hashes the password with scrypt, creates the account in an unverified state and issues a six-digit one-time code through the mailer. When an access code is configured, registration requires it before the username is examined. The user enters the code; the server verifies it against the stored hash and, if it is correct and unexpired, marks the account verified and sets a session cookie. If Google sign-in is configured, the user may instead obtain an ID token from Google, which the server verifies before it links the account and sets the same cookie. An account may also carry a second factor. When the user turns it on from the interface, the server issues a shared secret and an `otpauth://` address that Google Authenticator and every other authenticator app can read, and the secret stays pending until the user proves the app works by entering a code generated from it. From that point on the password alone does not open the account: the server answers the sign-in with a challenge, withholds the session, and issues it only when the challenge is met with a valid code.

**Step 2: File selection and upload preparation.** The authenticated sender selects a file in the browser, either through the file field or by dragging it onto the field, and chooses a recipient from the list of registered users. The interface accepts files up to 25 MB and shows the upload progress. The sender also chooses the permission and the self-destruct lifetime: never, one hour, one day or seven days. The browser turns the lifetime into an absolute moment, so that the expiry the file dies at is chosen by the sender and sent with the share rather than set by the server. An extra protection choice offers either the key alone or a password as well, and a password field appears when the second is chosen. The browser displays a short fingerprint derived from the recipient's public key, so that the sender can see which key the file will be encrypted to.

**Step 3: Client-side encryption.** The sender's browser generates a fresh AES-GCM 256-bit key and a random 96-bit initialisation vector, encrypts the file, and produces the ciphertext. It also computes a SHA-256 fingerprint of the plaintext. The plaintext file is not transmitted at any point.

**Step 4: Authorised sharing.** The browser encrypts the AES key with the recipient's RSA-OAEP public key, producing the wrapped key. It signs the string `from|to|filename|size|sha256 of the plaintext|iv|permission|expiry` with the sender's signing key. The signed string includes the permission and the absolute expiry moment that the sender chose, so both travel inside the signature and a recipient can rebuild the same string from the metadata. Where password protection was chosen, it derives a key from the password with PBKDF2 and wraps the same AES key a second time with AES-KW.

**Step 5: Secure transmission.** The browser uploads the ciphertext, the initialisation vector, the wrapped key, the second wrapped key when there is one, the signature, the protection mode, the password salt, the recipient name, the filename, the size, the permission, the expiry moment and the plaintext fingerprint. The server writes the ciphertext to a blob file on disk, records the share metadata in the JSON store with the expiry moment the sender sent, refusing one that is in the past or more than thirty days away, and appends a send event to the audit trail.

**Step 6: Recipient authentication.** The recipient signs in with the verified account and lists the shares addressed to that account. The server returns the share metadata, including its state, signature, protection mode, password salt, second wrapped key and expiry, only to the sender and the recipient; any other user receives 403. The metadata is returned even when the bytes are no longer served, so that a card can state that a share has expired or been revoked.

**Step 7: Decryption and integrity check.** The recipient's browser reads the private key from IndexedDB, unwraps the AES key with RSA-OAEP, and decrypts the ciphertext with AES-GCM. For a password-protected share it also asks for the password, derives the same key with PBKDF2 over the stored salt, recovers the AES key from the second wrapped copy and checks that it is the same key the private key recovered; neither wrap alone opens the file. The browser then recomputes the SHA-256 fingerprint of the recovered bytes, compares it with the fingerprint that travelled with the share, rebuilds the signed string from the metadata and verifies the sender's signature against the sender's published signing key. The status line reports both checks separately. If the fingerprint and the signature both hold, the file is fully verified; if the fingerprint differs, the browser reports that the recovered file is not the one that was sent; if the signature fails, it reports that the metadata was not vouched for by the sender. The first open is recorded with the server, which appends an open event to the audit trail. If the permission is download, the browser saves the file. If the permission is view, the browser opens the decrypted content without offering a save action. The server is not involved in this step.

Three lifecycle events can occur after a share has been sent. The sender may revoke a share that the recipient has not opened: the server records the revocation, appends a revoke event to the trail, and thereafter refuses the bytes with 410. The recipient cannot revoke a share and receives 403, and a share that has already been opened can no longer be revoked and receives 409. Separately, when the expiry moment set in step 2 passes, the share becomes expired and the bytes are refused with 410 in the same way. Third, the sender or the recipient may delete a share, which moves it to the trash: its bytes are refused exactly as they are for a revoked or an expired share, and the record stays in place so that the trash view can offer a restore. A restored share returns to the ordinary views, and its bytes are served again if it is still live. The sender alone may purge a trashed share, which removes the record and deletes the ciphertext file for good; this is the one operation that actually deletes stored ciphertext. A share therefore moves from live to one of three resting states, revoked, expired or trashed, and in each of them the server refuses the bytes while the metadata stays visible so that the card can state the reason. The server refuses to hand over the bytes; it does not claim to have erased them except at a purge.

Every send, open, revocation, delete, restore and purge appends an entry to the audit trail. Each entry carries the SHA-256 of the entry before it, so an entry cannot be altered or removed without breaking the chain that follows it. `GET /api/activity/verify` walks the chain and reports whether it is intact. The trail is filtered per account: an account sees the events attached to shares it sent or received, and never another account's events.

Three flows surround those steps and need to be stated on their own.

**Signing at the moment of the share.** Every account has an ECDSA P-256 signing key pair beside its RSA-OAEP key pair. The private half is non-extractable and lives in the browser with the RSA private key; the public half is published with the account and returned by `GET /api/users` as `signingKey`. When the sender creates a share, the browser signs the string `from|to|filename|size|sha256 of the plaintext|iv|permission|expiry` and sends the signature with the share. The permission and the expiry are inside the signed string because the recipient relies on both when it decides what it may do with the file: a server that quietly changed the permission or moved the expiry would break the signature instead of quietly granting the change. The server stores it and returns it with the share metadata. When the recipient opens the file, the browser rebuilds exactly that string from the metadata and verifies the signature against the sender's public key, and the interface says whether the signature checks out. The chain this creates is the point. The signature covers the plaintext fingerprint, and the fingerprint covers the bytes that arrived after decryption, so the signature proves who vouched for the file while the fingerprint proves that the file is the one that was vouched for. One check alone would not answer both questions. The signature is over metadata and not over the ciphertext, so an attacker who holds the server's data cannot forge a different file under the same signature, but the server can still refuse to deliver a share it has been told to refuse.

**Wrapping the file key twice when a password is set.** The sender may choose, when sending, that the file is protected with a password as well as with the recipient's key. The file key is then wrapped twice: once with the recipient's RSA public key and once with a key derived from the password, using PBKDF2 with SHA-256 and 210,000 iterations over a random sixteen-byte salt. The second wrap uses AES-KW. The password must be at least ten characters long. The password never reaches the server; the server stores the salt and the second wrapped key. The recipient is asked for the password when they open the file, in a panel in the interface. The browser opens both wraps and checks that they name the same key, so neither the recipient's key nor the password alone is enough.

**The recovery flow on a new device.** At registration, in the browser, the RSA key pair is generated extractable once. A recovery phrase of twelve words is generated from a built-in list of 128 words, and a key is derived from that phrase with PBKDF2, SHA-256, 210,000 iterations and a random salt. The private key is exported as PKCS#8 and encrypted with that key under AES-GCM. The encrypted form, with its salt and its IV, is uploaded to the server and also kept in the browser, while the device keeps a non-extractable copy of the private key for daily use by importing the same PKCS#8 bytes with `extractable` false. The phrase is shown once on a panel and offered on the sign in screen for a new device. The flow on a new device is: sign in with the password, then enter the phrase, and the browser fetches the encrypted blob, unwraps it locally and installs the private key. `POST /api/keys/backup` stores the blob for the signed in account, `GET /api/keys/backup` returns it, and `POST /api/keys/recover` returns it for a named account before there is a session, so that a new device can fetch it. The server cannot read the blob, and the server cannot reset the phrase. Twelve words drawn from a 128 word list gives 84 bits of entropy, which is strong against an online guess and weaker than a modern password manager, and the phrase is only as safe as the paper it is written on. Because the server holds the encrypted blob, a server compromise exposes it to an offline attack on the phrase, which is exactly why the derivation is deliberately slow.

**The second factor from an authenticator app.** The factor is a time-based one-time password, computed as RFC 6238 describes it and as every authenticator app expects. The server keeps a 160-bit random secret for the account, encoded in base32, and the app keeps the same secret. The code is the last six digits of an HMAC-SHA1 over the number of the current thirty-second step, taken from the dynamic truncation of the digest. The server recomputes the code from the secret and the step, accepts the current step and one step either side of it, so that a clock a little fast or a little slow still works, and compares the candidate codes in constant time so that the time taken does not say which one matched. A code is six digits and is therefore worth one part in a million, so the challenge behind it is short-lived and can be attempted only a few times. The interface shows the secret once, in groups of four, together with the `otpauth://` address that an app reads, and the factor is not live until the user has entered a code generated from it. Turning the factor on and off both require a valid code, so a session that is already open cannot be used to remove it, and the server records both events in the audit trail. Two properties are worth stating plainly. The factor works with no network and no mail service, because the code is derived from a secret and the clock and not sent by anyone. And because the secret is shared between the app and the server, a server that holds it could generate a valid code itself; that is true of every authenticator app, and it is why the factor is a second factor and not a second key. The email one-time code remains in place for the first sign-in, because it proves that the address belongs to the person who registered; the authenticator code proves that the person signing in also holds the device.

1. Input: file F, recipient R with encryption key K_R and signing key S_R, permission P, expiry moment EXP chosen by the sender, protection mode M.
2. Generate K, a fresh AES-GCM 256-bit key.
3. Generate IV, a random 96-bit initialisation vector.
4. Compute H = SHA-256(F), the fingerprint of the plaintext.
5. Compute CF = E(K, F) under AES-GCM with IV.
6. Compute CK = E(K_R, K) under RSA-OAEP.
7. Compute SIG = Sign(S_sender, "from|to|filename|size|H|IV|P|EXP").
8. If M is password, derive K_pw = PBKDF2(password, salt) and compute CK2 = AES-KW(K_pw, K).
9. Send CF, IV, CK, CK2 when present, SIG, M, salt, R, filename, size, P, EXP and H to the server.
10. The server stores CF as a blob, records the share with EXP, the fingerprint, the signature and the protection mode, refuses an EXP that is in the past or more than thirty days away, stores the EXP it was given so that the stored value is the one that was signed, and appends a send event to the trail.
11. On the recipient's request, return CF, IV, CK, CK2, SIG, M, salt and H to R only, and only while the share is live.
12. In R's browser recover K = D(K_priv, CK). If M is password, prompt for the password, derive K_pw, recover K2 = AES-KW^-1(K_pw, CK2), and check that K2 = K; refuse the file when the two keys differ, because neither wrap alone opens it.
13. Compute F' = D(K, CF, IV).
14. Compute H' = SHA-256(F'), rebuild the signed string and verify SIG with S_sender. Present F' as verified when H' = H and the signature holds, and record the first open.
15. If the sender revokes the share before step 14, or if EXP has passed, or if either party has moved the share to the trash, step 11 refuses with 410 and the metadata reports the state.

The decryption path in step 12 and step 13 is the inverse of the encryption path, and it is the point at which the design's central claim is either true or false. For a password-protected share the browser opens both wraps: it unwraps CK with the recipient's private key and CK2 with the key derived from the password, and it proceeds only when the two recovered keys are identical. Neither wrap alone opens the file, so the recipient needs the device that holds the private key and the password, and the password is at least ten characters long. Because the private key never leaves the recipient's device and the server never receives the AES key, the server cannot perform these steps. Step 14 adds two narrower checks: the fingerprint establishes that the bytes the recipient recovered are the bytes the sender fingerprinted, and the signature establishes that the metadata, and therefore the fingerprint within it, was vouched for by the sender. The verification in Chapter 4 tests both.

## 3.7 Data Held by the Server and the HTTP Interface

The server's state is deliberately small and can be inspected directly. User records contain the username, the email address, the scrypt salt and hash, the public key, the signing key, the wrapped private key backup with its salt and initialisation vector, a verification flag, the shared secret of the second factor when one has been turned on, the Google subject when the account was created through Google sign-in, the time the account was last active and a timestamp. Session records map an opaque token to a username and an expiry. A pending sign-in record holds a challenge token, the account the challenge is for, the moment it stops being valid and the number of wrong codes entered against it, and a pending factor record holds a secret that has been issued but not yet confirmed. Share records contain the identifier, the sender, the recipient, the filename, the size the sender reported, the number of bytes the server actually stored, which is the ciphertext length and not the length of the file that went in, the initialisation vector, the wrapped key and, when the share is password protected, the second wrapped key and the password salt, the signature, the protection mode of key or password, the permission, the expiry moment the sender set, which the server stores unchanged after refusing one that is in the past or more than thirty days away, the revocation time, the time of the first open, the plaintext fingerprint, the name of the blob file, the list of accounts that have starred the share, the time it was moved to the trash, the account that moved it, a timestamp and a derived state of live, expired, revoked or trashed. Activity records contain a timestamp, an event type, the actor, the share, the filename, the other party, an optional detail and the hash of the entry before them. The ciphertext itself is stored as a separate binary file, one per share. There is no field anywhere in this state for a usable private key, an AES key or plaintext; the one private key the server holds is encrypted under a key derived from the recovery phrase, and the server holds neither the phrase nor the derived key.

The shares endpoint returns four lists, `inbox`, `sent`, `starred` and `trashed`, and each entry carries `starred`, `deletedAt`, `deletedBy` and a `state` of `live`, `revoked`, `expired` or `trashed`. A live starred share appears in the starred list as well as in the inbox or sent list it came from, and a share in the trash appears only in the trash.

The key endpoints exist so that a new device can recover the private key without the server being able to read it. `POST /api/keys/backup` and `GET /api/keys/backup` require a session and operate on the signed-in account. `POST /api/keys/recover` is public because its purpose is to return the wrapped blob to a browser that has no session yet. It returns only the blob with its salt and initialisation vector, for a named account, and it is useless without the phrase. `GET /api/users` returns `signingKey` beside `publicKey`, so that a recipient can verify a share. `POST /api/register` and `POST /api/google-signin` accept `signingKey`, and `POST /api/shares` accepts `signature`, `protected`, `passwordSalt` and the second wrapped key `passwordWrappedKey`; the share metadata returns all four.

The access column is the enforcement point for the unauthorised-access scenario. A request for a share or its blob is accepted only when the authenticated session belongs to the sender or the recipient; otherwise the server returns 403. The blob is refused with 410 when the share has expired, been revoked or been moved to the trash, while the metadata is still returned so that the card can state the reason. Revocation is restricted to the sender and is refused with 409 once the recipient has opened the share. A star, a delete and a restore are accepted from either party to the share, while a purge is accepted only from the sender and only once the share is in the trash. The cipher-head endpoint returns only the first bytes the server really holds, and only to the two parties, so that the evidence panel can compare them with the sender's file without exposing the rest of the blob. The backup endpoints are confined to the signed-in account, while the recover endpoint is the one deliberate exception in this table: it returns only ciphertext that the server cannot open.

Static files under the public directory are served without authentication, because they contain only the interface and no user data. `GET /api/config` is public in the same way: the Google client id is public by design and the client secret never leaves the server.

The Google path is the only place where the server accepts an identity from outside. `POST /api/google-signin` passes the token to `server/google.js` before any account is linked. The check is on the server because a token accepted by the page would be accepted on the word of the page, and the page is controlled by the party whose identity is in question. The module verifies the algorithm, the issuer, the audience and the expiry, then the signature against Google's published keys. It uses `node:crypto` and the built-in `fetch` only, so the zero-dependency property is preserved.

Three further controls are visible at this layer. Sign-in is locked for fifteen minutes after five failed attempts and answers 429 while the lock holds; a one-time code is limited to five attempts; and an account may hold at most two hundred shares, beyond which the server answers 429. The password minimum is eight characters, and `/api/logout-all` ends every session of the account. The second factor is a further control on the same line: the password is checked first, the session is withheld until the challenge is answered, the challenge expires after five minutes, and five wrong codes against it end it. Every response also carries the security headers listed in Table 3.2, and the content security policy names the site's own script and styles, together with Google's identity script and the stylesheet its button needs when that path is configured, as the only permitted sources. The referrer policy sends the origin and nothing more, which is what Google's sign-in button requires. When `ACCESS_CODE` is set, registration requires it and the comparison is made before any other validation, so a stranger cannot learn which usernames exist.

Presence is a last-seen note rather than a live connection. When a signed-in account makes a request, the server records the time in `lastSeen`, and `GET /api/users` returns it with the public key, so that the people list can say when someone was last seen. The design stops there on purpose. A live indicator would need a websocket or a polling loop, and either would add a connection that the zero-dependency, zero-cost constraint cannot carry. A stored time costs nothing beyond a field and a write, and it answers the useful question, which is whether a person has been around recently, without pretending to know whether they are at the keyboard this second. The record is written at most every thirty seconds so that a busy session does not rewrite the store on every request.

## 3.8 Testing Procedure

Verification was carried out in two independent layers, because each layer can catch a class of defect that the other cannot.

The first layer is a **Node self-test** that exercises the server contract directly. `npm test` runs two suites in this layer, the server self-test and the Google verification test, and reports twenty-one checks. The suites use Node's built-in Web Crypto implementation, which is the same API the browser uses, so the cryptographic operations in the test are the same operations that run in the client. The test registers three users, one of whom is the intended third party. It asserts that an unverified account cannot sign in and that a wrong one-time code is rejected with 401. It verifies the three accounts, then encrypts a file for one user and uploads it. It asserts that the stored blob contains no plaintext, that the recipient decrypts the ciphertext back to the original bytes, that the sender and recipient each see the share in the correct list, and that the third user neither sees the share nor can fetch its blob, receiving 403. It then asserts that the demo access code is required at registration, that an expired share refuses its bytes with 410 and reports its state, that the sender can revoke while the recipient cannot, and that a share which has already been opened can no longer be revoked. It reads the activity trail as each user and asserts that the events are recorded and that another account's events are hidden, and it calls the chain verification endpoint and asserts that the chain is intact. It asserts the two abuse controls as well: repeated failed sign-ins are locked out with 429, and repeated wrong one-time codes are refused in the same way. It asserts that signing out everywhere ends every session of the account, so that the token used after the call is refused with 401. It asserts the share lifecycle as well: starring is per user and the starred list follows it, a deleted share leaves the sent list and enters the trash, a share in the trash refuses its bytes with 410, a restore brings the share back, and a purge removes it for good. The Google suite asserts that the client id is published, that a valid token signs a user in and preserves a key that the account had already published, and that a token with a wrong audience, a wrong issuer, an expired time, a tampered payload, a forged signature or a malformed structure is refused. The test runs against a temporary data directory that is removed afterwards, so it cannot disturb a demonstration's data.

The second layer is a **headless browser test**. `npm run test:browser` launches Chrome or Edge in headless mode and drives the real interface over the DevTools protocol, using Node's built-in WebSocket so that no test dependency is added. Two separate browser profiles are launched, one for each user, so that cookies and IndexedDB are genuinely separate; a test that used two tabs in one profile would share the key store and would not prove anything about isolation. The test registers two users through the real forms and asserts that the private key stored in the first user's IndexedDB is present and non-extractable. It sends a PDF through the share panel, asserts that the dashboard counts the share, that the evidence panel shows bytes different from the sender's, that exactly one blob exists on disk, and that the blob does not contain the marker string planted in the file. It sends a second file with a one-hour lifetime, and asserts that the card carries the permission and the self-destruct timer. It revokes that second share, asserts that the revoked badge appears, and reads the activity panel to confirm that the sends were recorded. It then reads the recipient's dashboard and asserts that both shares are listed, that both are marked unopened, that the revoked share is marked and cannot be opened, and that the heading names the inbox. Finally it decrypts the PDF through the interface, asserts that the recovered bytes equal the original, and asserts that the card then carries the verified badge and that the activity panel records the open. It also drives the file-drive workspace: it asserts that the rail shows the Starred and Trashed sections with their counts, that selecting a card shows the bulk bar, that starring a share puts it in the starred list, that deleting a share moves it to the trash and that the recipient cannot open it, and that restoring brings it back. It asserts that each account has a twelve-word recovery phrase and a wrapped private key on the server, that the sender's signature checks out when the recipient opens the file, and that a password-protected share refuses the wrong password and opens with the right one. The phrase panel, the restore line on the sign in screen and the password panel are driven through the real interface rather than called directly. Because the whole run is made against the real server, it also exercises the security headers: the page and its script are loaded under the content security policy, so a policy that blocked the site's own script or styles would stop the run. Screenshots are captured during the run and are the six figures in Chapter 4.

Both layers were run on the same machine. The self-test establishes the server contract in isolation, including the endpoints for expiry, revocation, starring, the trash, the activity trail and Google sign-in; the browser test establishes that the contract is reached through the actual interface and that the client performs its cryptographic steps, its integrity check and its signature check. A defect in either layer is therefore localised: a failure confined to the self-test points at the server or the HTTP interface, while a failure confined to the browser test points at the client script or the interaction between the two.
